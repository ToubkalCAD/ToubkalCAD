● Here's what was wrong and what changed:

  Root cause — TreeContextMenu.tsx

  The doExtrude, doRevolve, and doLoft handlers were still calling the OLD
  showParamModal → createShape path from before Phase 5. createShape added the
  node without params.opType / params.targetWireIds, which caused two problems:

  1. Nothing appeared in the tree — this was actually intermittent: if window.oc
  wasn't ready yet, the OCC computation threw silently, and createShape was
  never reached. The bigger issue was that the new Op3DPanel (the Phase 5 panel)
  was never opened from the context menu at all.
  2. Couldn't preview or modify — even when createShape did succeed, it stored
  no params.opType so the tree's double-click re-edit path (REEDITABLE check)
  always returned false.

  The fix (one file, 3 handlers)

  TreeContextMenu.tsx:
  - doExtrude → show3DOpPanel('extrude', [firstWireId])
  - doRevolve → show3DOpPanel('revolve', [firstWireId])
  - doLoft → show3DOpPanel('loft', wireIds)
  - Removed all now-dead OCC service imports, createShape, getDir, reg

  What you now get when right-clicking a sketch and choosing 
  Extrude/Revolve/Loft:
  1. The Op3DPanel floats open with a height slider and live blue-tinted preview
  in the viewport
  2. Adjusting the slider rebuilds the preview in real time (250 ms debounce)
  3. Clicking Apply ✓ adds the node to the tree with params.opType stored
  4. Double-clicking the extrusion in the tree re-opens the panel in EDIT mode
  (orange header, "Update ✓" button)
  5. Esc cancels and clears the preview

  SketchOverlay, Viewport3D, and everything else in Phases 1–4 are untouched.

  Root cause: show3DOpPanel and createAndEditOp relied on a module-level
  variable _opener = setOp3DReq that was set during CADLayout's render. When
  createAndEditOp called _opener(...) inside the same React event tick as

  batch as the Zustand updates.

  - createAndEditOp calls show3DOpPanel(op, targetIds, id) at the end instead of
  calling _opener directly

  - Added useEffect that listens for cad-open-op3d-panel and calls
  setOp3DReq(detail) — this runs in a fresh event tick, outside any Zustand
  batch, so React reliably processes it

  Window events are dispatched synchronously, but the listener is called in a
  clean execution context (the useEffect's callback is not inside the same React
  batch as the Zustand updates). This is exactly why all the other
  cross-component signals in this app (cad-add-mesh, cad-remove-mesh,

● Zero errors. Here's what was added and how it works:

  Smooth zoom-to-cursor — replaces OrbitControls' built-in zoom (which always
  zooms toward the orbit target, not the mouse):

  - Zoom focus: on each scroll event, a ray is cast from the mouse position. If
  it hits a solid mesh, the zoom focuses on that hit point. If it hits empty
  space, it falls back to the intersection with the orbital plane through the
  current target — so zooming over empty space still feels correct.
  - Velocity + damping: instead of snapping instantly, each scroll event adds to
  a velocity value (clamped to ±0.6). Each animation frame moves the camera a
  fraction of the distance toward the focus point, then multiplies velocity by
  0.78. This gives a smooth ease-out coast — like macOS trackpad momentum. The
  camera and orbit target both move together, so rotation still orbits the right
  point after zooming.
  - Distance-proportional movement: step = dist * vel means zooming is fast when
  far away and precise when close — the behavior Fusion 360 and Blender users
  expect.

  The SketchOverlay and all HTML overlays are untouched — the wheel listener is
  on renderer.domElement (the WebGL canvas), not the container div.

  1. Tree hierarchy — operations adopt their source sketch

  New store action adoptSketchSources(opId, wireIds): when you

  under the operation node. The tree now reads exactly as you wanted:

  tangled with a previous extrusion.

  2. Draggable panels

  react-draggable never actually worked here (its transform offsets from the
  element's flow position, which with position:fixed+portal lands off-screen —
  that was the original Op3D off-screen bug too). I removed it entirely and
  added a tiny dependency-free useDragPanel hook. PlaneSelector, Op3DPanel, and 
  BlendActionPanel now drag by their header and won't block the viewport.

  3. Zoom

  Switched to an immediate zoom-to-cursor registered on window with
  {capture:true} — capture phase fires before Dockview can swallow the wheel
  event (Dockview was the culprit all along). Each scroll dollies the camera
  toward the 3D point under your cursor.

  4. Enter / Esc

  All three panels: Enter = Apply/Confirm, Esc = Cancel. (When you're typing in
  a numeric field, Enter stays in the field; click away or use the slider and

  What's happening

  Your app loads opencascade.full.wasm = 48 MB — the entire OpenCASCADE kernel
  (every modeling class OCCT has, whether you use it or not). I checked how it's
  served:

  - ✅ Content-Type: application/wasm + the loader uses instantiateStreaming —
  so it compiles while downloading (already optimal there).
  - ❌ Served uncompressed (gzip/brotli not enabled) — 48 MB goes over the wire
  raw.
  - ❌ No Cache-Control header — so every reload may re-download and re-compile
  the whole 48 MB.

  Is it normal? Yes. The full opencascade.js build being huge and taking several
  seconds is a well-known characteristic. The cost is two parts:
  1. Transfer — 48 MB (fast on localhost, painful over a real network).
  2. Compile/instantiate — CPU-bound, a few seconds, and unavoidable with the 
  full build (compression does not reduce this).

  Optimization options, ranked by payoff

  #: 1
  Change: Cache-Control: immutable on the hashed wasm
  Effect: After the first load, reloads are near-instant (browser disk cache +
  V8
     compiled-code cache). Doesn't help the very first load.
  Effort: 2 lines

  #: 2
  Change: Custom slim opencascade.js build (only the ~20 classes you use)
  Effect: The only thing that cuts compile time. 48 MB → likely 8–15 MB → both
    faster download and faster compile.
  Effort: Moderate (Docker build)
  ────────────────────────────────────────
  #: 3
  Change: Brotli/gzip for production
  Effect: Download 48 → ~13 MB (gzip) / ~11 MB (brotli). Helps network deploys;
    negligible on localhost.
  Effort: Build config + server header
